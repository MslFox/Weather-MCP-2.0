# План реализации v2

## Статус

Ожидает одобрения пользователя. До одобрения этого плана нельзя менять исходный код, тесты или README в `weather-mcp`.

## Цель

Добавить новый MCP-инструмент `find_safe_weather_window`, который ищет будущий интервал по московскому времени и возвращает самое безопасное погодное окно для наружных работ, сохраняя поведение существующих инструментов.

## Архитектурное решение

Использовать существующую модель риска как единственный источник порогов. Добавить search-oriented путь сервиса: один раз определить город, одним запросом загрузить hourly-прогноз Open-Meteo для всего интервала поиска, нарезать прогноз на локальные окна-кандидаты, оценить каждого кандидата через `assessRisk` и ранжировать кандидатов локально.

Не вызывать `OpenMeteoRiskService.assess` отдельно для каждого кандидата, потому что это нарушит требование одного forecast-запроса.

## Правила входа

- `city`: trim-строка, 1..120 символов.
- `work_type`: `maintenance`, `installation` или `inspection`.
- `search_start`, `search_end`: московское время, `YYYY-MM-DDTHH:mm`.
- `duration_hours`: целое число, 1..8.
- `search_start >= now`.
- `search_end > search_start`.
- `search_end <= now + 5 days`.
- Кандидаты стартуют с первого полного московского часа не раньше `search_start`, затем каждый час.
- Конец кандидата должен быть `<= search_end`.
- Если не помещается ни один кандидат, вернуть контролируемую ошибку входа до запроса погоды.

## Контракт ответа

При успехе `structuredContent` должен быть стабильным и должен совпадать с JSON-текстом в `content[0].text`:

```json
{
  "kind": "safe_weather_window",
  "location": {
    "city": "Dubai",
    "region": null,
    "country": "United Arab Emirates",
    "timezone": "Asia/Dubai"
  },
  "query": {
    "city": "Dubai, United Arab Emirates",
    "work_type": "maintenance",
    "search_start": "2026-09-28T08:00",
    "search_end": "2026-09-28T18:00",
    "duration_hours": 3,
    "input_timezone": "Europe/Moscow"
  },
  "selected_window": {
    "start_at": "2026-09-28T09:00",
    "end_at": "2026-09-28T12:00",
    "period": {
      "start_utc": "2026-09-28T06:00:00.000Z",
      "end_utc": "2026-09-28T09:00:00.000Z"
    },
    "risk_level": "LOW",
    "recommendation": "PROCEED",
    "factors": [],
    "hourly_weather": []
  },
  "alternatives": [],
  "checked_candidates": 8,
  "source": "Open-Meteo",
  "fetched_at": "2026-09-27T12:00:00.000Z"
}
```

Неизвестный город должен возвращать MCP-ошибку вида `not_found`. Неоднозначный город должен возвращать MCP-ошибку вида `ambiguous` с вариантами. Сбои Open-Meteo должны возвращать `WEATHER_UNAVAILABLE_MESSAGE`, `isError: true` и не возвращать частичный `structuredContent`.

## Шаги реализации

1. Добавить time-helper-функции в `time.ts`, не меняя поведение `parseWorkPeriod`:
   - парсинг московского локального datetime;
   - форматирование UTC-дат обратно в московский `YYYY-MM-DDTHH:mm`;
   - парсинг и валидация интервала поиска;
   - генерация `WorkPeriod`-кандидатов от стартов на полный час.

2. Осторожно отрефакторить `open-meteo.ts`:
   - сохранить внешнюю совместимость `OpenMeteoRiskService.assess`;
   - извлечь общее определение города, чтобы `assess` и новый search-метод использовали одинаковое поведение для unknown/ambiguous;
   - извлечь загрузку и парсинг hourly-прогноза для произвольного `WorkPeriod`;
   - добавить метод вроде `findSafeWindow(request)`, который при успешном входе делает один geocoding-запрос и один forecast-запрос.

3. Добавить оценку кандидатов:
   - для каждого кандидата выбрать forecast-часы, пересекающие кандидата;
   - вызвать `assessRisk(candidateHours)`;
   - построить результат кандидата с московским стартом/концом, UTC-периодом, risk result, factors и hourly weather;
   - отсортировать comparator-ом: risk rank, количество факторов, UTC timestamp старта.

4. Добавить MCP-инструмент в `index.ts`:
   - строгая Zod-схема;
   - успешный ответ с JSON в `content` и совпадающим `structuredContent`;
   - маппинг `WeatherDataError` на общее сообщение недоступности;
   - маппинг `InputError` на контролируемую MCP-ошибку.

5. Обновить тесты:
   - MCP listTools содержит новый инструмент, старые инструменты остаются доступными.
   - Happy path возвращает выбранное окно, альтернативы, число проверенных кандидатов, source, location и fetched_at.
   - Тесты ранжирования покрывают уровень риска, меньшее число факторов при равном риске и более раннее окно при полном равенстве.
   - Генерация кандидатов покрывает неполные границы поиска и отсутствие кандидатов.
   - Валидация входа отклоняет плохую дату, прошлый интервал, интервал дальше пяти суток, неверный work_type и нецелую/вне диапазона длительность.
   - Unknown/ambiguous city errors не запрашивают forecast и не выбирают окно.
   - Сбой Open-Meteo возвращает контролируемую ошибку и не возвращает частичный результат.
   - Успешный search делает один geocoding-запрос и один forecast-запрос.
   - Существующие регрессии `get_weather`, `assess_weather_risk` и `compare_weather_windows` продолжают проходить.

6. Обновить `weather-mcp/README.md`:
   - описать вход, выход, ранжирование, ошибки и пример для `find_safe_weather_window`;
   - не ломать документацию существующих инструментов.
