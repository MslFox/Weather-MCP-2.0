# Карта зависимостей

## Runtime-зависимости

- `@modelcontextprotocol/server`: MCP-сервер и регистрация инструментов.
- `zod`: входные схемы MCP-инструментов.
- Open-Meteo Geocoding API: преобразует текст города в варианты локаций.
- Open-Meteo Forecast API: возвращает hourly-прогноз.

## Внутренние зависимости

- `index.ts` зависит от `open-meteo.ts`, `time.ts`, `cache.ts`, MCP и Zod.
- `open-meteo.ts` зависит от `cache.ts`, `risk.ts` и `time.ts`.
- `risk.ts` независим и должен остаться единственным источником погодных порогов риска.
- `time.ts` независим и содержит helper-функции парсинга московского времени.

## Предлагаемое направление новых зависимостей

Сохранить простое направление зависимостей:

- Добавить общие экспортируемые helper-функции/типы в `open-meteo.ts` или небольшой внутренний модуль, если так будет чище.
- `index.ts` должен вызывать метод сервиса для `find_safe_weather_window`, а не дублировать запросы и парсинг Open-Meteo.
- Новая npm-зависимость для базовой задачи не нужна.

## Тестовые зависимости

- Встроенный Node test runner.
- `@modelcontextprotocol/client` и `InMemoryTransport` для MCP-тестов.
- Mock `fetch` для детерминированного поведения Open-Meteo.

## Границы внешних сбоев

- Сбой геокодирования, HTTP-ошибки, битый JSON, некорректные hourly-данные, отсутствие покрытия по часам и timeout должны превращаться в контролируемые MCP-ошибки.
- Неизвестный или неоднозначный город — ожидаемые пользовательские ошибочные состояния, а не сбой внешнего сервиса.
