# Главный промпт домашней работы Weather MCP 2.0

Идентификатор задачи: HW-WEATHER-Lisin

## Цель

Реализовать в `weather-mcp` новый MCP-инструмент `find_safe_weather_window`. Инструмент ищет будущий интервал по московскому времени и возвращает самое безопасное погодное окно для наружных работ.

## Исходный контекст

- Требования находятся в `ЗАДАНИЕ.md`.
- Исходный проект находится в `weather-mcp`.
- Артефакты планирования находятся в `artifacts/HW-WEATHER-Lisin/`.
- Не менять исходный код до одобрения `artifacts/HW-WEATHER-Lisin/implementation-plan-v2.md`.

## Ограничения

- Сохранить существующее поведение `get_weather`, `assess_weather_risk` и `compare_weather_windows`.
- Не менять существующие публичные контракты без явного одобрения пользователя.
- Не дублировать пороги риска; использовать существующую модель риска.
- Использовать Zod-схему для входа нового инструмента.
- Загружать прогноз для всего интервала поиска одним внешним forecast-запросом.
- Возвращать контролируемые MCP-ошибки для невалидного входа, неизвестного/неоднозначного города и сбоев Open-Meteo.
- При сбое Open-Meteo не возвращать частичный результат.
- Не включать секреты или токены в артефакты.

## Критерии приёмки

- `find_safe_weather_window` виден через MCP `listTools`.
- Валидный вход возвращает выбранное окно, до трёх альтернатив, число проверенных кандидатов, город/локацию, источник и fetched_at в `structuredContent`.
- Кандидаты начинаются каждый полный московский час и полностью помещаются в запрошенный интервал.
- Весь интервал находится в будущем и в пределах пяти суток.
- Ранжирование использует `LOW < MEDIUM < HIGH`, затем меньшее число факторов, затем более ранний старт.
- Неизвестные и неоднозначные города не выбираются автоматически.
- Существующие инструменты сохраняют прежнее поведение.
- После реализации проходит `npm run ci`.

## Роли

- Analyst: извлекает требования, описывает текущую архитектуру, находит риски и границы.
- Planner: создаёт небольшой, проверяемый и совместимый с существующими инструментами план реализации.
- Critic: ищет контрпримеры, пропущенные тесты и логические ошибки до реализации.
- Builder: реализует только после одобрения `implementation-plan-v2.md`.
- Tester: добавляет и запускает автоматические и ручные проверки после реализации.
- Reviewer: проводит финальный review diff после реализации.
