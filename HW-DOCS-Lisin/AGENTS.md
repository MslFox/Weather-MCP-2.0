# Правила для AI-агента

## Область действия и допустимые изменения

Этот файл действует внутри `HW-DOCS-Lisin/`. Правила сопровождения кода ниже служат памяткой для задач по Weather MCP и сами по себе не дают разрешения менять соседний каталог. Перед работой прочитайте [корневой Agent.md](../Agent.md), следуйте корневому `AGENTS.md` и загружайте только промпт текущего этапа из `agents/`.

- В текущей задаче разрешено изменять только `README.md`, `AGENTS.md` и `CONTEXT.md` в этой папке. `HANDOFF-REPORT.md` должен оставаться пустым до отдельного запроса пользователя.
- В будущей задаче по реализации можно изменять относящиеся к ней файлы `weather-mcp/src/`, `weather-mcp/test/` и документацию, если это входит в запрос пользователя.
- `package.json`, `package-lock.json`, `tsconfig.json` и `Dockerfile` меняйте только при необходимости для поставленной задачи; изменение зависимостей объясняйте в отчёте.
- Не редактируйте вручную `node_modules/` и результат сборки `dist/`. Не меняйте пользовательские настройки MCP, секреты и посторонние файлы. Не удаляйте чужие изменения.

## Контракты, которые нельзя ломать без согласования

1. Сохраняйте STDIO-транспорт и четыре имени инструментов: `get_weather`, `assess_weather_risk`, `compare_weather_windows`, `find_safe_weather_window`. Не выводите диагностические сообщения в STDOUT.
2. Сохраняйте схемы входа и структуру ответа из `weather-mcp/src/index.ts` и типы из `weather-mcp/src/open-meteo.ts`, включая `structuredContent`, текстовое содержимое и признак `isError`.
3. `get_weather` принимает `days` от 1 до 7. Инструменты планирования принимают время по Москве без смещения в строке; расчёты выполняются в UTC. Период начинается не раньше текущего момента и заканчивается в пределах пяти суток от него.
4. Сохраняйте допустимые типы работ и связь `LOW → PROCEED`, `MEDIUM → REVIEW`, `HIGH → CANCEL`. Риск периода определяется худшим затронутым часом. Пороговые значения и строгие температурные границы закреплены в `risk.ts` и тестах.
5. При сравнении сохраняйте порядок двух окон, `window-1`/`window-2` и индексы от нуля. При равном риске возвращайте `tie: true` и `selected_indices: []`; дополнительные критерии выбора здесь не применяются.
6. При поиске сохраняйте длительность 1–8 целых часов, начало кандидатов на полном часе и ранжирование по риску, числу факторов и раннему старту. Возвращайте не более трёх альтернатив; не представляйте окно с высоким риском как разрешение на работы.
7. В инструментах оценки и поиска не выбирайте неоднозначный город автоматически: возвращайте до пяти вариантов. Не выдумывайте погоду и не возвращайте частичный успешный результат при неполном прогнозе.
8. Сохраняйте кэш успешных прогнозов и оценок в памяти: TTL 10 минут без продления при чтении, до 500 записей на экземпляр. Ошибки не кэшируются; просроченные данные не выдаются при сбое обновления.
9. `/health` включается только при заданном `HEALTH_PORT`, слушает `127.0.0.1` и отвечает на `GET /health` кодом 200 с `{"status":"ok"}`.

## Обязательные проверки

- При изменении кода из `weather-mcp` выполните `npm run ci`: сборку TypeScript и полный набор тестов. Добавляйте содержательные проверки нового поведения и исправляемых ошибок.
- При изменении только документации сверьте имена инструментов, ограничения и команды с кодом и `package.json`; проверьте относительные ссылки и отсутствие секретов. Новые тесты для текста не нужны.
- Если изменён Dockerfile, проверьте сборку и healthcheck при доступном Docker. Если проверка недоступна, сообщите об этом; не заявляйте успешную проверку контейнера.
- Результаты локальных тестов не выдавайте за проверку живого Open-Meteo или внешнего развёртывания.

## Когда задать вопрос пользователю

- Не определены бизнес-правила, целевой проект или границы задачи; требования противоречат друг другу.
- Требуется менять публичный контракт, пороги риска, трактовку времени, архитектуру или выполнять миграцию данных.
- Не хватает доступа или внешнего подключения, необходимого для результата.
- Планируется необратимое действие, публикация, merge, deploy либо изменение внешней системы: соблюдайте подтверждение, требуемое корневым процессом.

Для однозначных обратимых изменений в разрешённой области дополнительное подтверждение не требуется.

## Что считать готовым результатом

Запрос пользователя выполнен в согласованной области, контракты сохранены, необходимые проверки реально пройдены, документация соответствует реализации. В итоговом сообщении указаны изменения, результаты проверок и оставшиеся ограничения. Артефакты и состояние задачи ведутся по применимым этапам корневого `Agent.md`; неподтверждённые релизы и проверки нельзя отмечать выполненными.

Для текущей задачи в `HW-DOCS-Lisin/` должны находиться ровно четыре запрошенных файла: три заполненных документа и пустой `HANDOFF-REPORT.md`.
