# Контекст Weather MCP

Дата актуальности: 29 сентября 2026 года. Описание основано на коде и тестах каталога `weather-mcp/`.

## Что уже реализовано

- Локальный MCP-сервер версии `1.0.0` с четырьмя инструментами: `get_weather`, `assess_weather_risk`, `compare_weather_windows`, `find_safe_weather_window`.
- Получение координат, текущей погоды, дневного и почасового прогноза через Open-Meteo без API-ключа.
- Оценка риска наружных работ по температуре, вероятности осадков и ветру; поясняющие факторы содержат время, показатель, значение и уровень риска.
- Сравнение двух периодов с сохранением обоих результатов и явным обозначением равного риска.
- Поиск лучшего периода с почасовым шагом и выдачей до трёх альтернатив.
- Проверка входных данных и полноты прогноза, обработка ошибок внешнего сервиса, уточнение неоднозначного города в инструментах планирования.
- Кэш успешных результатов `get_weather` и оценки риска в памяти процесса на 10 минут, до 500 записей на экземпляр. Сравнение использует кэш оценок; отдельного кэша поиска окон нет.
- Необязательный HTTP endpoint `/health`, многоэтапный Dockerfile на Node.js 24 Alpine и локальная команда сборки с тестами `npm run ci`.

## Основные архитектурные решения

| Модуль | Ответственность |
| --- | --- |
| `src/index.ts` | Создание MCP-сервера, регистрация инструментов и схем Zod, обычный прогноз, сравнение окон, формирование MCP-ответов и запуск STDIO. |
| `src/open-meteo.ts` | Геокодирование для планирования, запрос и проверка почасовой погоды, оценка периода и поиск окон; типы результатов. |
| `src/risk.ts` | Чистая функция расчёта риска и факторов, без сетевых запросов. |
| `src/time.ts` | Разбор московского времени, перевод в UTC, проверка пятисуточного горизонта, построение кандидатов и пересечение часов. |
| `src/cache.ts` | Нормализация названия города и ограниченный кэш с TTL. |
| `src/health.ts` | Проверка работоспособности локального HTTP listener. |
| `test/*.test.mjs` | Тесты на встроенном runner Node.js с загрузкой TypeScript через `tsx`. |

Пути в таблице указаны относительно `weather-mcp/`. Используются TypeScript в строгом режиме, ESM, MCP SDK и Zod; сборка помещается в `dist/`. Сетевые функции и часы можно подменять для воспроизводимых тестов.

Основной поток: MCP-запрос → проверка аргументов и периода → кэш, если применим → геокодирование → прогноз → проверка данных → расчёт → MCP-ответ. Для поиска один прогноз покрывает весь интервал; кандидаты оцениваются локально.

Время работ всегда вводится по Москве (UTC+3); почасовой прогноз для расчёта запрашивается в UTC, часовой пояс города сохраняется как информация о локации. Скорость ветра в модели риска измеряется в м/с.

Итоговый риск равен максимальному риску среди затронутых часов:

| Уровень | Вероятность осадков | Ветер | Температура | Рекомендация |
| --- | --- | --- | --- | --- |
| `HIGH` | ≥ 70% | ≥ 15 м/с | < −15 °C или > 40 °C | `CANCEL` |
| `MEDIUM`, если нет `HIGH` | ≥ 40% | ≥ 10 м/с | < −5 °C или > 32 °C | `REVIEW` |
| `LOW` | Ни один порог выше не сработал | — | — | `PROCEED` |

Сравнение двух окон учитывает только итоговый уровень риска. Поиск при одинаковом уровне дополнительно сравнивает число факторов и время начала.

## Известные ограничения и проблемы

- Горизонт планирования — пять суток; поиск допускает только целую длительность 1–8 часов и начало кандидатов на полном часе. Обычный прогноз допускает 1–7 дней.
- `work_type` проверяется и сохраняется, но пороги одинаковы для всех трёх типов работ. Название `find_safe_weather_window` не гарантирует низкий риск: даже выбранное окно может иметь рекомендацию `CANCEL`.
- `get_weather` берёт первый результат геокодирования. Оценка, сравнение и поиск требуют уточнения неоднозначного города; поведение инструментов здесь различается.
- Обработка сетевых запросов разделена между `index.ts` и `open-meteo.ts`. Для обычного прогноза установлен тайм-аут 10 секунд, для сервиса риска — 5 секунд на запрос. В сервисе риска таймер снимается после получения ответа до чтения JSON, поэтому это не строгий предел времени обработки всего тела ответа.
- Кэш не сохраняется после перезапуска. Нет базы данных, постоянной истории прогнозов или автоматического повторения неудачных внешних запросов.
- MCP доступен через STDIO. HTTP listener обслуживает только healthcheck, а не MCP; его ответ не проверяет доступность Open-Meteo.
- В существующем `weather-mcp/README.md` остались примеры абсолютных путей с другого компьютера и дат в прошлом. В новых инструкциях используется относительный путь и пример без фиксированной даты.
- Dockerfile подготовлен, но сборка контейнера и внешнее развёртывание в этой задаче не проверялись. Доступность живого Open-Meteo также не проверялась.

## Подтверждённые проверки

29 сентября 2026 года из каталога `weather-mcp/` выполнена команда `npm run ci` на Node.js `20.20.2` и npm `10.8.2`. Сборка TypeScript завершилась успешно; все 33 теста прошли, ошибок и пропусков нет. Погодные ответы в тестах подменяются, а healthcheck проверяется локально. Проверка живого API и контейнера в этот результат не входит.

## Что можно делать дальше

1. Заполнить `HANDOFF-REPORT.md` по отдельному запросу пользователя.
2. Проверить сервер через MCP Inspector с реальным погодным запросом; отдельно проверить Docker-сборку и healthcheck.
3. Обновить устаревшие пути и примеры дат в основной документации.
4. Унифицировать геокодирование и обработку сетевых запросов после согласования изменений поведения; распространить тайм-аут на чтение тела ответа.
5. При необходимости согласовать разные пороги для типов работ, затем добавить реализацию и тесты.
